# LXMF

`LXMF` implements the inventoried required LXMF 1.2.1 software contracts through native APIs on [DotReticulum](https://github.com/dennispayne/DotReticulum). Message signing/validation, delivery proofs, proof-of-work, persistent tickets and ratchets, paper-message ingestion, message containers, opportunistic/direct delivery, propagation delivery, authenticated retrieval and propagation storage exist. Explicit and autonomous peer synchronization are Python-live-verified in both directions, including native daemon restart and failed-peer recovery. A NativeAOT `lxmd` executable exists. Optional client rendering, intentional native differences, upstream defects and verification boundaries are recorded below; this is not an exhaustive-parity claim.

## Message format and API

An LXMF message contains `destination(16) || source(16) || signature(64) || msgpack([timestamp, title, content, fields[, stamp]])`. The message hash covers destination, source, and the payload without the stamp. The signature is validated during unpacking. `LxMessage` exposes generating, outbound, sent, delivered, rejected, failed, and cancelled states, plus completion tracking.

A typical application creates a router with a DotReticulum `TransportRouter` and an identity, registers its receive callback, starts it, announces its destination, and submits messages:

```csharp
var lxmf = new LxmRouter(transportRouter, identity, "dotnet");
lxmf.MessageReceived = received => Console.WriteLine(received.Message.Content);
lxmf.Start();
await lxmf.AnnounceAsync();
var message = LxMessage.Create(destinationHash, identity, "content", "title", fields: null, LxmMethod.Direct);
await lxmf.SendAsync(message);
var finalState = await message.Completion;
```

Dispose `LxmRouter` asynchronously with the transport router that owns it. `LxmRouterOptions` configures retry attempts (default 5), retry wait (10 seconds), path request wait (7 seconds), pathless tries (1), processing interval (4 seconds), inbound direct-resource transfer size (1,000,000 bytes), inbound stamp cost/enforcement, and optional opportunistic receipt timeout. `SendAsync` packs and queues the message; delivery runs in the background, so observe `State` or `Completion`.

## Security and access

Messages are signed and signature-validated. Opportunistic payloads are encrypted to the destination identity; direct delivery uses an encrypted Link. The router has no identity allow-list or application-level access-control policy for its inbound delivery destination. Configure an inbound stamp cost and keep enforcement enabled when proof-of-work gating is required; stamps do not replace peer authorization policy.

## Delivery behavior

Opportunistic delivery sends one encrypted packet and uses a delivery receipt. Its content ceiling is derived from the encrypted-packet MDU and message overhead (287 bytes for the pinned settings); larger messages requested as opportunistic are promoted to direct delivery. Direct delivery uses a Link: messages up to 319 bytes fit in one packet with the pinned settings; larger messages use a Resource. The router requests paths, retries failures, and suppresses duplicate received hashes for 180 days (upstream's `MESSAGE_EXPIRY * 6`), with a 65,536-entry bound. `StoragePath` persists this history in upstream's `local_deliveries` binary-key map before application callbacks. Incoming direct Resources are accepted only up to `DeliveryPerTransferLimit`.

`LxStamper` generates and validates 32-byte proof-of-work stamps. When a destination announces a stamp cost, outbound messages receive a stamp. A router may advertise and require an inbound stamp cost. Invalid delivery stamps are dropped when enforcement is enabled; otherwise the callback receives `StampValid=false`. As the actual router constructor and `lxmd` utility, delivery enforcement defaults to false. `EnforceStamps()` / `IgnoreStamps()` change the live policy. This does not disable mandatory propagation-node stamp validation. Ticket stamps are checked before ordinary work. `Tickets` provides issuance, renewal, expiry, grace and atomic upstream-compatible persistence; `IncludeTicket` requests automatic signed reply-ticket exchange. Keys expire after 21 days, renew inside 14 days, retain expired inbound keys for five-day cleanup grace, and suppress repeat issuance for one day after confirmed ticket delivery. `Save()` flushes explicitly; transactional `Reload()` replaces memory from the owned file without reopening the router. Missing or corrupt files preserve existing secret ownership, failed replacement is disposed/zeroed, and caller-owned ticket copies remain detached. Native reload reports malformed input through exceptions rather than silently accepting a corrupt store.

The delivery destination is `lxmf.delivery`. Announce data may carry a display name, inbound stamp cost and compression support. Advertised explicit lack of compression is honored for direct Resources. Delivery ratchets are enabled by default; `EnforceRatchets` rejects non-ratcheted opportunistic encryption. Configure `StoragePath` to persist signed upstream-compatible ratchet files in `lxmf/ratchets/<destination>.ratchets`; without a path the keys are memory-only. The router owns the ring, not the supplied identity or transport.

`SetInboundStampCost()` changes the advertised/enforced cost; values below one clear it and values at least 255 are rejected. Delivery announces and path responses update a bounded upstream-compatible `outbound_stamp_costs` map with 45-day expiry. The worker and graceful disposal flush dirty costs atomically; `SaveOutboundStampCosts()` explicitly flushes them. `GetOutboundStampCost()` consults the cache and known announce data.

Direct links identify the sender; opportunistic packets are encrypted to the destination identity or announced ratchet. Message callbacks execute serially on a separate bounded receive worker; duplicate messages are suppressed even without subscribers. One observer throwing does not prevent other observers or later processing. Inbound overload is explicitly logged and dropped (default capacity 256); outbound capacity (default 256) includes messages still preparing stamps. `Cancel(message)` or `CancelOutbound(messageId)` cancels preparation or an active Resource and releases capacity; disposal cancels pending completion tasks. Message-ID progress and target-stamp-cost lookups include deferred preparation. Messages expose stamp value/check/validation metadata.

Identified incoming delivery links provide backchannels for replies, without requiring a destination path or opening another link. Both link roles install receive/resource handlers and packet proving before sending; this includes proofs for packets received by the original initiator. Direct packets remain `Sending` until proved. Already-concluded receipts are checked after callback registration, and an active delivery link is usable immediately rather than waiting out its connection retry deadline. `CleanLinks()` closes outbound direct links strictly after 600 seconds without data and propagation links strictly after 180 seconds; node cleanup releases validation/transfer admission records. Maintenance checks links every four seconds and terminal delivery-resource tracking every eight seconds. Tests advance an explicitly controlled protocol clock with automatic stack timers disabled, then verify the exact boundaries and fresh-link recovery; this is not a real 600-second idle soak.

`CreateBinary` preserves arbitrary title/content bytes. Text conversion uses strict UTF-8: invalid titles throw, invalid content reports the decoding error and returns null, and unpaired input surrogates throw, matching the reference. `CreateUnassigned`, one-time source/destination assignment and pre-pack setters support deferred construction. Explicit timestamp zero is retained. For paper messages, create with `LxmMethod.Paper`, call `Pack(destinationIdentity: identity)`, then `AsUri()`. The URI is `lxm://` plus unpadded URL-safe base64 of `destination || encrypted(source || signature || payload)`, with an encrypted-size ceiling of 2210 bytes. `FromPaperUri` decrypts for the addressed identity or caller-owned `DestinationEndpoint` and validates the message; an optional decryptor supports a caller-owned ratchet ring. GROUP paper encryption/decryption has executed reference vectors. `AsUri()` finalizes with upstream's paper state `0x05` (not a network delivery confirmation). `IngestPaperUriAsync()` queues local delivery, reports rejected/local/duplicate results, supports explicit duplicate acceptance and persists processed transient IDs. As upstream, paper ingestion bypasses stamp enforcement and reports the propagated delivery method. Cancellation stops waiting, not an already queued delivery. Nonlocal paper forwarding is not a working pinned-source contract (see the defect/placeholder inventory below); native ingestion explicitly rejects it. Optional QR image rendering is not implemented.

`RegisterPlainDelivery()` additionally receives signed, unencrypted PLAIN packets without stamp gating. Actual Python router-originated PLAIN messages reach this endpoint. Native PLAIN packing matches actual reference bytes; receiving them through a registered Python PLAIN endpoint is **not verified working**: pinned RNS `Identity.recall` dereferences that endpoint's null identity while LXMF unpacks, and `LXMRouter.lxmf_delivery` separately assumes a registered SINGLE delivery policy. No reference shim bypasses either defect. Upstream `LXMessage.pack` raises `UnboundLocalError` for GROUP opportunistic messages; native code explicitly rejects that mode. Paper GROUP support does not establish GROUP network delivery.

`PackedContainer()` / `UnpackContainer()` preserve upstream's `state`, `lxmf_bytes`, `transport_encrypted`, `transport_encryption` and `method` MsgPack map. `WriteToDirectoryAsync()` writes and fsyncs a message-hash-named container before atomic replacement, serializing writes per message. The destination directory must already exist. `UnpackFromFileAsync()` reads a stable file handle with a configurable allocation ceiling (default 16 MiB), then restores and validates the container. Native file APIs throw contextual I/O/format exceptions instead of returning Python's `None`. Executed upstream file-writing/restoration vectors cover exact names and bytes; native tests cover concurrent replacement, cancellation, bounds and failure cleanup. Applications own these files; `lxmd` also writes its inbox atomically.

`FieldsValue` preserves the complete MsgPack field map, including nil, tuple, infinite and NaN keys and nested maps. `SetFields()` accepts a conventional dictionary and `SetFieldMap()` an ordered `MsgPackMap`; signing, containers and automatic reply-ticket updates preserve all entries. `TryGetField()` / `SetField()` address known numeric fields using Python numeric-key equality. The original `Fields` dictionary API remains available for conventional top-level maps; it explicitly throws for extended-key maps rather than silently dropping their entries. Nil fields normalize to an empty dictionary; other non-map field values are rejected, as in the actual reference.

## Propagation APIs

Set `OutboundPropagationNode` to an announced `lxmf.propagation` destination and send a message with `LxmMethod.Propagated`. Its completion means **Sent to the node**, not delivery to the final recipient. `RequestMessagesFromPropagationNodeAsync()` identifies this router, lists only its delivery destination's messages, decrypts them, and acknowledges deletion unless `retain: true`.

`EnablePropagationNode()` requires `StoragePath`; it creates encrypted `lxmf/messagestore` files, reloads the index on restart, validates PN stamps and enforces transfer/sync/storage limits. Its default app-data provider includes current propagation configuration in path responses even before an explicit announce, allowing static peers to discover it. `RequireAuthentication` and `AllowedIdentities` restrict downloads; `SetAuthentication`, `AllowIdentity` and `DisallowIdentity` update that policy at runtime. Control authorization has separate `AllowControl` / `DisallowControl` mutations. `FromStaticOnly` and `StaticPeers` independently restrict inbound deposits. Storage weight is `size * max(1, age_days / 4)`, reduced tenfold for `PrioritisedDestinations`; highest-weight entries are evicted first. Independently executed upstream weight/eviction vectors and an actual three-message propagation test cover priority survival. Unlike upstream's periodic over-limit cleanup, admission enforces the byte bound before writing; an incoming highest-weight message may be discarded, not reported as recipient-delivered.

`SynchronizePeerAsync()` performs `/offer`, peering-key proof-of-work, wanted-ID negotiation and encrypted Resource transfer. Offers use ascending storage weight, remove purged/low-stamp IDs, mark oversize or declined IDs handled and strictly exclude cumulative sizes equal to the sync limit. `SyncStrategy` defaults to persistent; `SetPeerSyncStrategy()` configures and persists an individual peer. Persistent peers reconnect and immediately offer remaining batches after successful transfers; lazy peers stop after one. Both close each completed transfer's link, as upstream does. Throttled senders retain queued IDs and defer for 180 seconds; scheduling respects that deadline. Peer transmission counters use completed Resource original-data size; transfer rates use its encrypted/compressed wire size, matching executed `LXMPeer.resource_concluded` cases. Actual compressed Resource completion verifies that these dimensions differ. Native rate calculation keeps its bounded minimum elapsed interval instead of reproducing source division by zero for a zero-duration observation.

Persistent `LxmPeer` snapshots retain only message IDs still in the store. Default scheduling is one serialized peer sync every 24 seconds, with 720-second incremental connection-failure backoff and 14-day discovered-peer expiry. Autopeer respects announced enabled state, hop depth and maximum accepted peering cost. Rotation runs every 1,344 seconds and preserves static peers; executed upstream cases cover lowest-acceptance selection and static protection. Incoming offers gate sequential validation and maximum inbound syncs (default 3), static peers may bypass these gates, and invalid-stamp Resources throttle identified peers for 180 seconds. Actual native process tests cover three stalled Resource advertisements, busy rejection, teardown/recovery, continued control service and real throttle expiry; they do not saturate three full payload streams simultaneously.

`MaxPeers` limits new discovered or explicitly added peers, not configured static peers or known-identity persisted peers: both startup exceptions work even with `MaxPeers=0`, matching the executed reference. Unknown-identity persisted peers are discarded; missing configured static peers are recreated and request paths. A native hard ceiling of 65,536 peer records bounds these exceptions and queues. Identified incoming Resources discover a peer from cached propagation app-data under the same enabled/autopeer/depth/cost gates, even when its path-response announce did not itself trigger peering.

Enabling, disabling/re-enabling and `ScheduleAnnounce()` schedule propagation announcements after the reference's 20 seconds. Each call retains its own absolute deadline; jobs do not coalesce or add another serial 20-second delay. The node owns and cancels this worker and bounds pending jobs at 256. Announcement data is read at send time, including the disabled flag. A configured extra control identity also causes a control-destination announce. `AnnounceAsync()` remains an explicitly immediate native extension.

`GetOutboundPropagationCostAsync()` uses cached valid PN configuration or requests a path and waits up to the medium-aware `PathRequestWait` for app-data. Message preparation uses the same discovery before generating work. Changing `OutboundPropagationNode` immediately retires a mismatched cached retrieval link. `InboundPropagationNode` is a detached alias, as the actual reference getter is; only configuring a separate inbound node is an upstream placeholder.

The separate `lxmf.propagation.control` destination implements `/pn/get/stats`, `/pn/peer/sync` and `/pn/peer/unpeer`. It authorizes the node's own identity plus `ControlAllowedIdentities`; being allowed to download does **not** grant control. `CompileStats()` exposes the corresponding message/peer/storage map. Native daemon control queries, valid queued peer sync and successful remote unpeer have actual network acceptance. Request/resource authorization reads the core remote identity, not asynchronous identity-observer side effects.

Client receive counters count accepted packets, including retransmitted deposits, not unique stored messages. Executed upstream duplicate-deposit observations and two native Link packets produce two received messages and one stored entry. Restart assertions preserve the observed packet count rather than incorrectly assuming that reliable delivery never retries.

## Limitations and differences from upstream

Optional QR rendering is not implemented. Required node admission, startup/reload, delayed announcement, retrieval/progress and failure-signalling contracts have source-generated and executable evidence. Final-library daemon NativeAOT/process acceptance passes on Windows and Linux; physical and exhaustive fault-matrix boundaries remain separate.

Messages expose source-blackhole status, ratchet/link ID and RSSI/SNR/quality. Router delivery applies the stack's identity-block policy to the signed message source before ticket/history mutation or application observation. `Unpack()` accepts an optional identity-blackhole predicate instead of a process-global Reticulum singleton; failed predicates are reported and leave status false, matching the source. Ratchet IDs are taken from per-operation decryption metadata or the actual direct link; caller mutations cannot change the stored ID. Physical telemetry is copied from packet/link observations, not synthesized; TCP loopback does not establish radio RSSI accuracy. Upstream 1.2.1 supports exactly one delivery identity per router; this is not a missing native multiple-identity contract. PLAIN reference reception and GROUP opportunistic packing have the defects described above. Signed ratchet-file cross-import and delayed old-key delivery after native/Python restart are Windows-live-verified. An `lxmd` configured with its default 1 KB `delivery_transfer_max_accepted_size` may reject larger Resources; this is peer policy, not a wire-format limit. Successful delivery to an `lxmd` destination does not establish propagation synchronization.

Stack `b8a1cc5` exposes source-verified `TransportRouter.FirstHopTimeout(ReadOnlySpan<byte>)`, `GetMediumPathTimeout()` and `GetLowestInterfaceBitrate()`. Runtime scheduling consumes these APIs: medium-aware path waits and round trips, 60-second slow-interface request debounce, slow-target ordering and global in-flight serialization, reduced attempt limits, airtime jitter and extended packet receipt deadlines. Path arrival releases a waiting attempt immediately; failed opportunistic delivery rediscoveries drop stale paths before re-requesting. `GenerateLxmSchedulingVectors.py` executes pinned `LXMRouter.py:1756–1824` and actual outbound processing with controlled medium inputs, path I/O, clock and jitter. Runtime debounce tests use in-process 1000/10000-bit/s interfaces; they are not physical slow-radio evidence. Custom native retry/processing options remain supported; configured maximum attempts remain an upper bound. Source direct attempts count connection attempts, not each packet sent on an already active link. There is no guessed medium fallback or reflection workaround. Existing public `Link.NoDataFor`, physical-layer tracking, `LocalDestination.DecryptWithMetadata` and identity-block checks are sufficient for their respective remaining work.

Stack `3cdf5be` initializes outbound activity after accepting an initiator LINKREQUEST, matching RNS `Link.py:318–321`. Its deterministic pending-link regression closes the idle-reconnection race caused by `LastData=0`; independent Linux full acceptance passed 114/114 with the corrected pin. LXMF does not reorder cleanup to conceal the stack lifecycle issue.

Propagation retrieval retains one identified active node link, expires it after strictly more than 180 idle seconds, and exposes progress, response size, last response/duplicate counts and a detached cached link ID. `CancelPropagationNodeRequests()` cancels the active path/link/Resource request, tears down the cache and resets state; `AcknowledgeSyncCompletion()` resets ordinary completion but preserves error states unless requested otherwise. Progress observers are isolated and optional. Node path discovery waits `max(10 seconds, PathRequestWait)`, including actual medium observations. Native request deadlines remain bounded, and response size/cancellation limits are installed before transport submission.

The executed retrieval oracle exposes two upstream defects: `retain_synced_on_node` suppresses known-ID acknowledgments, but newly downloaded messages are acknowledged/deleted even when retention is requested; returned encrypted bytes are acknowledged even when delivery rejects them. Native retention of newly downloaded messages and acknowledgment only after recognized/successfully decrypted data are intentional safety corrections, not exact reproduction of these destructive reference behaviors. Actual Python node acceptance verifies retention, later deletion, cached reuse and a cancelled/recovered 2.2 MB download with intermediate progress and response size.

Invalid propagation **packets** produce upstream's MsgPack `[0xf5]` rejection and teardown; the native sender associates that signal with the in-flight message and preserves terminal rejection through late receipts/timeouts. Transfers on the same propagation link are serialized while awaiting their outcome, avoiding the reference's stale `for_lxmessage` association on reused links. Actual Python rejection and subsequent valid-message recovery pass. Invalid **Resources** instead tear down and throttle the identified peer without an `0xf5` packet, as upstream does; strict expiry and observer-failure recovery are exercised separately.

## Required software disposition

The inventory's required message, delivery, ticket/ratchet, propagation client/node/peer, configuration, persistence, lifecycle and progress behaviors have native implementations and cited evidence. Python callback spelling, mutable implementation objects, threads, subprocess registries and deque polling are not copied as API requirements. `StateChanged`/`Completion`, router-owned transports and cancellable bounded async preparation implement their observable contracts.

Stamp preparation starts asynchronously rather than waiting for the Python four-second registry poll. Peer distribution updates bounded ID sets immediately rather than retaining Python's 24-second deque batch; it excludes the sending peer before exposing a new stored entry and marks successfully received IDs handled. Executed source distribution observations and actual Python peer transfers verify origin exclusion. These are explicit native scheduling differences, not claims to reproduce Python's worker architecture. Protocol maintenance retains four-second idle checks, eight-second terminal-resource cleanup, 240-second transient-cache cleanup, 24-second peer/throttle maintenance, 480-second store/state maintenance and 1,344-second rotation. Failed maintenance is logged and the owned worker continues.

`CleanTransientIdCaches()` enforces strict 180-day expiry for delivered and processed IDs, including while otherwise idle, and persists removals. `CleanThrottledPeers()` uses strict expiry and also runs on the 24-second job. The source-job oracle executes all 336 dispatcher ticks and actual cache/throttle boundary methods. Local cancellation tests interrupt a 2.2 MB incoming Resource through both inbound cancellation APIs, release tracking, and deliver the next message.

Restart tests load actual reference encrypted/stamped storage, remove only recognized native interrupted-write files, preserve committed bytes, reject hash corruption and release the exclusive lease after failed startup. Delivery/processed/stamp-cost and node peer/stat atomic-write remnants are cleaned by their owners. Live process restart and failure recovery are described separately below. Simulated interrupted files and process restarts are not storage-device power-loss testing.

Remaining deferrals are optional QR/client field rendering and codec/playback support explicitly optional in `LXMF.py`; nonworking upstream PLAIN/GROUP/nonlocal-paper behaviors and inbound-node differentiation; and external physical-radio/slow-medium accuracy or storage-device power-loss validation. No new required wire format or placeholder behavior is invented. Exhaustive combinations of every policy, filesystem failure and simultaneous full-payload saturation are not claimed verified merely because the corresponding gates execute.

## Platform notes

LXMF message and delivery formats are not OS-specific; actual network reachability depends on the configured Reticulum interfaces and their support on the host. Managed or loopback tests do not establish platform-wide interface support.

## Reference provenance and acceptance boundary
